Why we chose GitHub Projects:

  1. No seat cap that would block a 5-person team. Trello's Free tier
     is workable but Asana's 2-user Free cap is not; GitHub Projects is
     free with no user limit on the Free plan.
  2. It lives next to the code. FoodFast's source will be hosted on
     GitHub; a pull request that says "closes #12" moves the card to
     Done automatically, so the board never drifts far from reality.
  3. Custom fields (Number, Single-select) are enough to model Story
     Points, Priority, and Epic without paying for a heavier tool the
     team does not yet need.

2. PROJECT CHARTER

Name: FoodFast - campus food ordering platform.

Background: Small eateries around the university campus take orders
by phone or in person, which is slow at peak hours and error-prone.
Students want a faster way to order and pay without walking to a
crowded counter.

Objectives:
  - Let a student order food from a nearby campus eatery online and
    track it until delivery or pickup.
  - Let a small eatery manage its menu and incoming orders without
    new hardware.
  - Demonstrate a full Agile delivery cycle for the HSB2006 course
    deliverable, from requirements to a working backlog on GitHub
    Projects.

Success criteria:
  - A customer can complete the full order flow: browse, add to cart,
    pay or choose cash on delivery, and track status, end to end.
  - A restaurant owner can manage a menu and accept or reject an order.
  - All Must-priority stories in the backlog (Section 7) are Done by
    the end of Sprint 4, against the Definition of Done in Section 11.

Out of scope: multi-city expansion, native mobile apps, a courier
payroll system, and loyalty/rewards programs. These may become later
epics but are not part of this 8-week build.

Constraints: 5 team members, 8 hours per person per week, 8 weeks
total, zero budget (free-tier hosting and free-tier tools only).

Assumptions: the team has basic web development skills already; a
free-tier hosting and database provider (for example Vercel plus a
free-tier Postgres provider) is sufficient for the demo scale; no real
payment processor is connected, a sandbox/test mode is used instead.

8. DETAILED SPECIFICATION - THREE KEY STORIES

US-01: Customer registration with email OTP verification

  AC1 (happy path)
  Given a new customer on the registration screen
  When they submit a valid email and password and then enter the
  correct one-time code sent to that email
  Then the account is created and they are logged in

  AC2 (repeated wrong OTP entries)
  Given a customer has requested a one-time code
  When they enter an incorrect code 5 times in a row
  Then the code is invalidated and they must request a new one after
  a 5-minute cooldown

  AC3 (expired code)
  Given a one-time code was issued more than 10 minutes ago
  When the customer submits that code
  Then the system rejects it as expired and offers to resend a new
  code

  AC4 (duplicate account)
  Given an email address is already registered
  When someone tries to register again with that same email
  Then the system rejects the registration and suggests logging in
  or resetting the password instead

  AC5 (network loss mid-registration)
  Given a customer has submitted the registration form
  When the network connection drops before a server response is
  received
  Then the client shows a retry option and does not create a
  duplicate account if the original request actually succeeded
  server-side

US-10: Place an order choosing delivery or pickup

  AC1 (happy path)
  Given a customer has at least one item in their cart
  When they choose delivery, confirm an address, and submit the
  order
  Then an order is created with status "placed" and the restaurant
  is notified

  AC2 (network loss mid-order)
  Given a customer has pressed "place order"
  When the network connection drops before the client receives a
  confirmation
  Then the order is not created twice; on reconnect the client
  checks order status by a unique request ID before allowing another
  submit attempt

  AC3 (restaurant unavailable)
  Given a restaurant has marked itself closed
  When a customer tries to submit an order to that restaurant
  Then the order is blocked and the customer is told the restaurant
  is currently closed

  AC4 (empty cart)
  Given a customer's cart has zero items
  When they navigate to checkout
  Then the checkout screen is not shown and the customer is
  redirected back to the menu with a message

  AC5 (missing delivery address)
  Given a customer has chosen delivery
  When they have not provided a delivery address
  Then the order cannot be submitted until an address is entered

US-11: Pay by card at checkout

  AC1 (happy path)
  Given a customer has a valid order ready for payment
  When they submit valid card details
  Then the payment is authorised and the order proceeds to "paid"
  status

  AC2 (card declined)
  Given a customer submits card details
  When the payment gateway declines the charge
  Then the order stays unpaid, the customer sees the decline reason,
  and can retry with a different card

  AC3 (network loss mid-payment)
  Given a payment request has been sent to the gateway
  When the network connection drops before the client receives the
  result
  Then the system checks the gateway's authoritative transaction
  status before showing success or failure, so the customer is never
  charged twice for one order

  AC4 (session/payment timeout)
  Given a customer has started the payment form
  When more than 10 minutes pass without submission
  Then the session expires and the customer must re-enter payment
  details

  AC5 (retry after failure)
  Given a payment attempt has just failed
  When the customer corrects their card details and resubmits
  Then a new payment attempt is made without creating a second order

  Stories: US-01, US-02, US-03, US-04, US-05.
  Points: 5+3+3+3+3 = 17 (target band 20-22; under budget on purpose,

  Goal: a customer can search and filter the menu, build a cart, and

  Stories: US-06, US-07, US-08, US-09, US-10.

  Stories: US-11, US-12, US-13, US-14.

10. KANBAN BOARD DESIGN

  Column         WIP limit   Entry condition
  -------------  ----------  ---------------------------------------
  Backlog         none        Any story or task the team has agreed
                              is worth doing, refined or not.
  Ready            8          Story has acceptance criteria written,
                              is estimated in story points, and has
                              no unresolved dependency.
  In Progress      3          A developer has free capacity and
                              pulls the highest-priority Ready item;
                              a branch has been created for it.
  Code Review      3          A pull request is open, it builds, and
                              its automated tests pass locally.
  Testing          3          The pull request is merged to the
                              staging branch and deployed to the
                              staging environment.
  Done             none        The item has passed QA testing on
                              staging and meets every item in the
                              Definition of Done (Section 11).

WIP limits are set to 3 for the three active columns because the team
has two developer roles (Frontend, Backend) doing the hands-on build
work; a limit of 3 leaves one slot of slack without allowing the
column to become a queue.


11. DEFINITION OF DONE

A story is Done only when all six of the following hold:
  1. Code is merged to the main branch via a reviewed pull request.
  2. Automated tests are written and passing for the new behaviour.
  3. The story's own acceptance criteria (Section 8 style) all pass.
  4. The feature is deployed and verified on the staging environment.
  5. No known critical or high-severity bug is open against it.
  6. Any new user-facing text has been checked for the target
     language (English or Vietnamese) it was written for.

14. HOW TO BUILD THIS ON GITHUB PROJECTS

  1. In the GitHub organisation or personal account, go to Projects
     and create a new project.
  2. Choose the Board template so the default view is a Kanban board.
  3. Rename the default columns to match Section 10: Backlog, Ready,
     In Progress, Code Review, Testing, Done.
  4. Add a custom field of type Number named "Story Points".
  5. Add a custom field of type Single-select named "Priority" with
     options Must, Should, Could, Won't.
  6. Add a custom field of type Single-select named "Epic" with one
     option per epic from Section 6 (E1 to E7), or use labels in the
     form EPIC:<name> on each issue instead.
  7. In the repository, create one label per epic, in the form
     EPIC:account-auth, EPIC:discovery-search, and so on.
  8. Create one GitHub issue per user story from Section 7. Fill in
     the Story Points and Priority fields, and attach the matching
     Epic label.
  9. Add each new issue to the project board; it lands in Backlog by
     default.
  10. During Sprint Planning, drag the sprint's stories into Ready,
      then into In Progress as developers pick them up, following the
      WIP limits in Section 10.
  11. Link each pull request to its issue using "closes #<issue
      number>" in the PR description, so merging the PR moves the
      card to Done automatically once it also passes staging testing.
